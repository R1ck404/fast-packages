# @r1ck404/fast-es-module-lexer

A faster drop-in replacement for [`es-module-lexer@1.7.0`](https://www.npmjs.com/package/es-module-lexer):
the same exports (`ImportType`, `init`, `initSync`, `parse`), identical
results (object shapes, key order, values) and identical errors.

```jsonc
// package.json
"dependencies": { "es-module-lexer": "npm:@r1ck404/fast-es-module-lexer@1.7.0" }
```

| input | times faster than es-module-lexer 1.7.0, in Node | in Chromium |
|---|---|---|
| small modules (70B-1.6KB) | 3.2-7x | 2.4-4.4x |
| 0.5-1.2MB bundles | 6.2-17.6x | 5.2-7.9x |
| batches of real package files | 5-7.7x | 3.5-4.9x |

Times and inputs: [benchmark results](https://github.com/R1ck404/fast-packages#results).

Startup (Node, fresh processes): `import` 1.48 ms (es-module-lexer 1.56 ms),
`import` + `await init` + first parse 2.42 ms (2.63 ms), `import` +
`initSync()` + first parse 2.33 ms (2.24 ms).

Size: the browser bundle of `{ initSync, parse }` (esbuild, minified) is
21.6 KB / 9.3 KB gzip / 8.5 KB brotli (es-module-lexer: 14.1 / 6.5 / 5.8 KB);
the npm package 29.4 KB, 75.7 KB unpacked (es-module-lexer: 31.2 / 93.4 KB).
Most of the bundle is the lexer's wasm (16.6 KB, 6.9 KB gzip; es-module-lexer's
is 9.3 KB): the SIMD scanners and the inlined fast paths that make it fast.
The smallest build of the same code (the whole crate at `opt-level = "z"`)
is only 0.2 KB smaller after gzip and up to 13% slower.

## How

* `rust/src/lib.rs`: lexer.c ported function by function; the main loop only
  stops at the few characters that matter (SIMD nibble-table classifier over
  64-char blocks), strings/comments/templates/import clauses are skipped with
  SIMD.
* Getting the source into wasm: Node's `Buffer.latin1Write`/`ucs2Write`, a wasm
  loop over the JS-string builtins in Chromium, `TextEncoder.encodeInto`
  elsewhere; always one byte per UTF-16 unit, which is all the lexer needs.
* Results come back as one int array; specifiers without escapes are sliced
  instead of `eval`'d.
* Size: `no_std` without an allocator (source and records live in linear
  memory grown with `memory.grow`); the hot loops are inlined, the statement
  parsers and helpers are not, and their whitespace and keyword checks are
  inlined only for the common case (inside the source, no comment).
* One module: `index.mjs` is the code and the wasm (base64: Node decodes it
  in microseconds). Bundlers take `browser.mjs` for browsers (the `browser`
  export condition): the same code without the Node.js paths, with the wasm
  as a denser text (the 87 most frequent bytes one character, the others two;
  ~25% smaller than base64 after gzip) that a 356-byte wasm module decodes.

`index.mts` is the source of both (TypeScript, shipped as `.mjs`; `browser.mjs`
is generated by `build.mjs`). The `es-module-lexer/js` (asm.js) subpath is
not provided.

## Differences

On malformed code es-module-lexer can read memory outside its source: below
it (its bracket stack), past its end (the records of the imports and exports
found so far, then whatever earlier parses left there), or through a NULL
position. Its answer then depends on what it parsed before (and can differ
between two calls with the same source). This package answers such inputs
exactly as a **fresh** es-module-lexer instance does (its first parse):
`rust/src/lib.rs` computes what that instance's memory holds at each address
it reads, including the records, and traps where it traps. The answer does
not depend on history. (Tested against the original's own JS glue on a new
wasm instance, `test/original.mjs`: every input of `test/diff.mjs`,
`test/edge.mjs` and `test/browser.mjs` on which the lexer reads outside the
source, 2,636 of the corpus diff's, and 20,000 fuzzed ones in every copy
mode.) Where that differs from what you get:

* **Nesting deeper than 1024 open brackets** (`(`, `{`, `` ` ``, `${`)
  or 512 open `import(` calls: es-module-lexer's stacks overflow into its own
  copy of the source (or its bracket stack), and its answer goes wrong (e.g.
  `"(".repeat(1500) + ")".repeat(1500) + "; import 'a'"` is a parse error at
  column 2900; 600 nested `import(` a parse error at column 1). This package
  answers these correctly up to 16384 open brackets and 4096 open `import(`
  calls, and throws a parse error at the first one past that. Pinned in
  `test/edge.mjs` ("nesting").
* **Records that do not fit the original's memory** (a source that is mostly
  short exports, e.g. `export{a,a,a,...}` with ~20,000 names): a fresh
  es-module-lexer instance traps (`RuntimeError: memory access out of
  bounds`), and so does this package; an es-module-lexer instance whose
  memory grew in earlier parses answers instead. A trapped es-module-lexer
  instance traps on every later parse; this package keeps working. Pinned in
  `test/edge.mjs` ("records overflow"). (JavaScriptCore's message of a trap
  names the JS expression that called into wasm, so there the message text
  differs.)
* **Non-string arguments** go through es-module-lexer's own conversion
  (`length + 1` units filled by `charCodeAt`): the same results and the same
  TypeError / RangeError for `null`, `undefined`, objects without
  `charCodeAt`, negative lengths. An object that has `charCodeAt` but no
  `slice` / `lastIndexOf` is answered as the string of its chars, where
  es-module-lexer throws a TypeError calling them; a length past 4 GB throws
  a RangeError from the typed array rather than from `memory.grow`. Pinned in
  `test/edge.mjs` ("string-like object").
* `init` resolving after `initSync()` keeps the instance `initSync` made
  (es-module-lexer replaces it with a second one; not observable except as
  memory).

## Development

    node build.mjs            # cargo build (wasm32, simd128) + wasm-opt -> index.mts/index.mjs, browser.mjs
    npm test                  # edge cases (index.mjs, browser.mjs), quick corpus diff, bundle test
    npm run test:full         # full corpus in every copy mode, both modules, bundles, browsers (Chromium, Firefox, WebKit)

`test/hooks.mjs` loads a module with its internal test hooks exported (the
published modules export only es-module-lexer's API).
